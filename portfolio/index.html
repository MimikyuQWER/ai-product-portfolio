虚拟用户访谈平台
米哈游 · 原神国际化用户研究 · 纯前端单文件 · 离线可用

传统模式：真人访谈真人 → 受人力与语言限制速度慢 → 专业用研团队分析写报告 → 报告完成后原始数据不再利用 → 业务团队只能看到「二手信息」。

AI 时代的机遇：AI 访谈产品提升了效率与产出量，但用研团队面对激增的访谈数据，分析能力成为新瓶颈。

本项目的思路：用已有访谈与 BI 数据为真实受访者建立 AI 数字分身——用研调教分析 Skill → 激活数据资产 → 业务方和管理层直接对数字分身发起对话，获取一手用户洞察。目标闭环：AI 访谈真人 → 数据回收 → 用研产出报告并持续调优 → 数字分身作为资产持续迭代。

将用户研究员「筛选 → 访谈 → 对比 → 提炼」的完整工作流转化为可交互的 AI 工具：

筛选目标群体 → 选择用户进入访谈 → AI 检索档案生成回答 → 展开思考过程与信息源 → 群聊对比或画像合成
三个核心设计：
① 三级回答体系——原文可答 → 证据可推演 → 证据不足直说不编造，每条回答可追溯、可验证
② 50+40+10 评测体系——结论一致性(50分)·推理一致性(40分)·风格适当(10分)，每次迭代全量回归
③ 独立审计 Agent——主 Agent 回答后由审计 Agent 二次评估，bad case 分类归档、针对性调优

基于上千名真实玩家的访谈与 BI 数据 1:1 建模，每位虚拟玩家包含 20+ 档案字段（UID、付费金额、游戏时长、流失原因等）。支持 7 维度筛选（国家/性别/年龄/平台/付费等级/所属游戏/冒险等级），覆盖美国、英国、日本、俄罗斯等区域。已在米哈游用研团队作为访谈前的情景预演工具实际使用。

地址信息审核 Agent
腾讯 · 微信支付 KYC 风控 · Python + Streamlit · ReAct Agent 架构

微信支付在个人客户身份识别（KYC）环节，需要核验客户提交的居住或联系地址是否真实存在。传统做法是审核员逐条在百度地图和搜索引擎上交叉比对——一条地址平均耗时 3-5 分钟，批量审核数百条地址时效率极低，且不同审核员的判断标准不统一。项目初期只是一个大模型提示词实验，经过多轮数据驱动的迭代后，演进为一个完整的 ReAct Agent 系统。该方法论具有通用性，同样可扩展到商户资质审核、法律文书地址核验、企业注册信息验证等场景。

迭代过程 · 从提示词到 Agent：初版用万能公式（角色 + 任务 + 输出要求 + 示例）撰写基础提示词。每次用带人审标签的历史数据跑一轮，将 AI 结果与人审结果逐条对比——重点关注两者不一致的 case 和 AI 输出「不确定」的 case，归类观察原因，调整提示词。遇到有争议的边界 case 则咨询之前负责审核的同事和文档积累，将他们的判断逻辑逐一编码进提示词。在基座模型间交叉验证，最终将准确率从 80% 提升到约 95%，人力消耗降低约 1/3。

迭代过程中积累的核心经验——判断标准定义越细致，模型判断越准确——最终沉淀为 5 条量化审核标准：完整度≥6 级、可搜索核实、定位准确、门牌号可查、特定地点豁免。每条标准都包含正反面示例和边界 case（如「门牌号符合常见规范≠真实存在」「附近/旁边等模糊方位词→判不确定」），并给模型保留「不确定」的输出余地，严禁编造和假设推断。这些标准后来被重构为 ReAct Agent 的 System Prompt。

技术架构上，Agent 按 ReAct 模式（Think → Act → Observe → Answer）执行。每条地址先由 LLM 做格式和完整度初判，信息不足时主动追问；确认后并行调用高德地图 geocode 和 Bing 搜索进行交叉验证；最终对照 5 标准输出四列审核报告（序号、地址、结论、依据+可点击链接）。支持单条输入和 Excel 批量上传，审核结果汇总为结构化表格。

实际使用中团队最认可的设计：预审报告环节。Agent 在调用任何外部 API 之前，先向用户展示数据摘要——共多少条、每条完整度评估（缺省/市/区/街道/门牌号）、哪些明显无效、预计 API 调用次数——用户确认后才进入正式审核。这个设计避免了大量无效 API 调用和 Token 浪费，也保持了审核员对流程的控制感。

已在腾讯金融业务团队作为客户 KYC 审核辅助工具实际使用，处理过真实地址数据。当前 Demo 版本使用示例数据展示审核流程与判断逻辑，核心 Agent 架构与生产版本一致。
