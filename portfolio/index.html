虚拟用户访谈平台

米哈游 · 原神国际化用户研究 · 纯前端单文件 · 离线可用

传统模式：真人访谈真人 → 受人力与语言限制速度慢 → 专业用研团队分析写报告 → 报告完成后原始数据不再利用 → 业务团队只能看到「二手信息」。

AI 时代的机遇：AI 访谈产品提升了效率与产出量，但用研团队面对激增的访谈数据，分析能力成为新瓶颈。

本项目的思路：AI 访谈真人 - 用回收的访谈结果与 BI 数据为真实受访者建立 AI 数字分身——专业用研团队调教分析 Skill、产出中间层研报 → 激活数据资产 → 业务方和管理层直接对数字分身发起对话，获取一手用户洞察。目标闭环：AI 访谈真人 → 数据回收 → 用研产出报告并持续调优 → 数字分身作为资产持续迭代。

将用户研究员「筛选 → 访谈 → 对比 → 提炼」的完整工作流转化为可交互的 AI 工具：

筛选目标群体 → 选择用户进入访谈 → AI 检索档案生成回答 → 展开思考过程与信息源 → 群聊对比或画像合成

三个核心设计

  • 三级回答体系——原文可答 → 证据可推演 → 证据不足直说不编造，保证 AI 每条回答可追溯、可验证，减少黑盒不信任感
  • 端到端 + 过程评测体系——建立黄金评测集，从结果端和每个中间环节设计验收标准，每次迭代保证黄金评测集效果不退步
  • 独立审计 Agent——主 Agent 回答后由独立审计 Agent 二次评估，bad case 分类归档、针对性调优

基于上千名真实玩家的访谈与 BI 数据 1:1 建模，每位虚拟玩家包含 20+ 档案字段（UID、付费金额、游戏时长、流失原因等）。支持 7 维度筛选（国家/性别/年龄/平台/付费等级/所属游戏/冒险等级），覆盖美国、英国、日本、俄罗斯等区域。已在米哈游用研团队作为访谈前的情景预演工具实际使用。

地址信息审核 Agent

腾讯 · 微信支付 KYC 风控 · Python + Streamlit · ReAct Agent 架构

微信支付在个人客户身份识别（KYC）环节，需要核验客户提交的居住或联系地址是否真实存在。传统做法是审核员逐条在百度地图和搜索引擎上交叉比对——一条地址平均耗时 3-5 分钟，批量审核数百条地址时效率极低，且不同审核员的判断标准不统一。项目初期只是一个大模型提示词实验，经过多轮数据驱动的迭代后，演进为一个完整的 ReAct Agent 系统。该方法论具有通用性，同样可扩展到商户资质审核、法律文书地址核验、企业注册信息验证等场景。

迭代过程 · 从提示词到 Agent：初版用万能公式（角色 + 任务 + 输出要求 + 示例）撰写基础提示词。每次用带人审标签的历史数据跑一轮，将 AI 结果与人审结果逐条对比——重点关注两者不一致的 case 和 AI 输出「不确定」的 case，归类观察原因，调整提示词。遇到有争议的边界 case 则咨询之前负责审核的同事和文档积累，将他们的判断逻辑逐一编码进提示词。在基座模型间交叉验证，最终将准确率从 80% 提升到约 95%，人力消耗降低约 1/3。

迭代过程中积累的核心经验——判断标准定义越细致，模型判断越准确——最终沉淀为 5 条量化审核标准，每条都包含正反面示例和边界 case，并给模型保留「不确定」的输出余地，严禁编造和假设推断：

  • 完整度 ≥ 6 级——省/市/区/街道/门牌号逐级评估
  • 可搜索核实——关键要素能在公开渠道检索到
  • 定位准确——地图坐标与地址描述一致
  • 门牌号可查——注意「门牌号符合常见规范 ≠ 真实存在」
  • 特定地点豁免——「附近/旁边」等模糊方位词 → 判不确定

这些标准后来被重构为 ReAct Agent 的 System Prompt。

技术架构上，Agent 按 ReAct 模式（Think → Act → Observe → Answer）执行。每条地址先由 LLM 做格式和完整度初判，信息不足时主动追问；确认后并行调用高德地图 geocode 和 Bing 搜索进行交叉验证；最终对照 5 标准输出四列审核报告（序号、地址、结论、依据 + 可点击链接）。支持单条输入和 Excel 批量上传，审核结果汇总为结构化表格。

实际使用中团队认可的设计：预审报告环节。Agent 在调用任何外部 API 之前，先向用户展示数据摘要——共多少条、每条完整度评估（缺省/市/区/街道/门牌号）、哪些明显无效、是否需要使用者补充信息或做核对——用户确认后才进入正式审核。这个设计避免了大量无效 API 调用和 Token 浪费，也保持了审核员对流程的控制感。

已在腾讯金融业务团队作为客户 KYC 审核辅助工具实际使用，处理过真实地址数据。当前 Demo 版本使用示例数据展示审核流程与判断逻辑，核心 Agent 架构与生产版本一致。

每日 AI 资讯日报

18 个固定内容快照 · React + TypeScript · 阅读、编辑、导出一体

AI 行业的信息更新很快，但内容分散在公司博客、Product Hunt、GitHub、论文平台和个人博客中。逐个平台浏览不仅耗时，同一事件还可能被不同渠道重复报道；大量一手信息是英文长文，收藏链接也不等于真正完成阅读和理解。

本项目的判断：用户不是缺少信息，而是缺少一个稳定的“信息压缩和阅读入口”。因此将新闻聚合、去重、正文清洗、图片本地化和 AI 中文摘要连接成完整链路，最终输出一份每天 5-10 分钟可以读完、还能继续编辑和带走的结构化日报。

完整产品链路：RSS / 网站信息源 → 抓取与字段标准化 → 去重、正文清洗、图片本地化 → AI 生成中文标题、摘要、价值说明和标签 → 日报阅读、编辑、导出与发布。作品集 Demo 保留最后一段“日报体验”和必要的轻量服务，不公开抓取器、数据库、调度器、发布账号与内部文档。

三个核心设计

  • 固定快照优先——公开 Demo 使用真实生成结果的固定快照，不在面试现场重新抓取新闻；18 个日期与 401 张新闻图片全部本地保存，稳定复现优先于“看起来实时”
  • 阅读与编辑合一——阅读模式用于快速浏览，编辑模式直接处理 Markdown；草稿按日期保存在当前浏览器，支持最多 5 步撤销 / 重做，并可随时恢复原始快照
  • 安全降级与原文保护——基础阅读、编辑和导出不依赖 API Key；AI 润色按二级标题分段处理，单章节失败就保留原文，结果只进入本地草稿，永远不覆盖固定快照

日报结果可以一键复制 Markdown、下载 Markdown 或导出带完整样式的独立 HTML。桌面端采用“日期 - 正文 - 目录”三栏结构，窄屏下将日期切换为选择器和导航抽屉，让第一次接触项目的人先完成阅读，再按需要逐步进入编辑、导出和 AI 润色。

本地结构化知识库系统

159 页 Markdown · 量化金融 + AI 产品双领域 · AI 可检索、可维护、可溯源

AI 的知识不能只靠每次对话的上下文——对话结束就清零。于是搭建了一套结构化个人知识库，让 AI 能跨 session 持续积累和检索知识。不是简单的笔记堆砌，而是有 Schema、有索引、有溯源机制的工程系统。

三层知识体系：
① 数据流入层——飞书知识库每日增量同步（SHA-256 去重）+ PDF/PPTX 研报 MarkItDown / pdfplumber 双工具对比择优转换 → 存入 raw/
② 结构化层——4 种页面类型（Entity / Judgment / Pattern / Observation），统一 frontmatter 元数据，[[wikilink]] 交叉引用图
③ 检索层——渐进式披露设计（大纲索引 50 行掌握全貌 → 详细内容 → raw/ 原始材料），时效性标记自动提醒过期数据

核心设计理念：每条事实性陈述必须可溯源到 raw/ 原文。不确定就标注「待补充」，不允许用常识填空。raw/ 目录对 AI 只读，防止编造内容污染原始素材。每次更新自动 git commit，形成可追溯的知识演进历史。

AI 协作闭环：
① 摄入——读研报 / 笔记 → 提取要点确认 → 结构化写入对应页面 → 更新索引
② 沉淀——对话结束后提取新判断 / 事实 / 方法 → 写入 wiki → 检查与已有内容矛盾
③ 答疑——飞书笔记自动检测疑问句 → 查 wiki 框架性知识 + iFinD 实时数据 → 给出可溯源答案
④ 健康检查——定期扫描 inbox 积压、孤立页面、矛盾判断、过期数据

知识来源两条线：飞书知识库每日自动同步（SHA-256 增量去重，token 过期自动刷新）+ 本地研报 PDF/PPTX 双工具择优转换（MarkItDown + pdfplumber 对比评分，质量检查通过后入库）。飞书笔记中的疑问句被自动扫描识别后，优先从 wiki 结构化页面检索框架性知识，wiki 没覆盖的再从 raw/ 原始材料深挖，确保每一条回答可溯源、不编造。
