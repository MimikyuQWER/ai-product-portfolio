# Harness Engineering — AI 开发工程约束框架

> 人类掌舵，智能体执行。好的 harness 比好的 prompt 更重要。

## 核心公式

```
Agent = Model + Harness
```

同一模型在不同 Harness 下的表现差异，远大于不同模型在同一 Harness 下的差距。

---

## 一、开发流程约束

### Demo → MVP → 可用版本 三阶段

**Demo 阶段**：
- 把主链路和关键节点整理出来，证明想法值得看
- 定义理想的输入态、交互态、输出态
- 数据可以先用假数据填充
- 目标："把想法讲清楚，体验演出来"

**MVP 阶段**：
- 主链路真实可跑（从输入到输出有真数据）
- 核心接口和工具真实可用
- 范围足够小，只保留核心模块
- 关键决策：本轮验证什么核心目标？哪些做哪些不做？

**可用版本**：
- 稳定使用、可迭代
- 失败路径和异常处理完备
- 工程化、稳定化

### Git 铁律

AI 每完成一个相对独立的任务就提交一次 commit。开新功能开新分支。验收完成后合并主干。

关键节奏：
1. `pull` 同步最新 → `git status` 确认工作区干净
2. 切分支隔离任务
3. AI 动手改
4. `git diff` 确认改了什幺
5. commit checkpoint
6. push / 提交协作

**高压线**：严禁 AI 将代码上传到 GitLab/GitHub。

## 二、Agent 集群设计

### 何时需要多 Agent

- 行为模式互斥，需要清楚分工
- 专业化能力：持续工作、持续迭代、非一次性
- 场景复杂，单个 AI 上下文无法理解或完全遵守
- 系统复杂、容错率低、持续使用

### 编排模式选择

```
有几条业务线？
├─ 1-2条 → 先用单 Agent，别搞复杂
└─ 3条以上 → 业务之间共享底层能力吗？
    ├─ 完全不共享 → 按业务线拆（像公司按事业部）
    ├─ 有共享 → 按职能/能力域拆（搜索Agent、SQL Agent、写入Agent等）
    └─ 部分共享 → 混合模式（核心能力做职能Agent，个别独立业务做专属Agent）
```

核心原则：**能力沉淀在 Agent 里，业务逻辑沉淀在流程编排里。**

### 集群 Agent 的 JD（四要素）

每个 Agent 必须说清楚四件事：

**1. 我做什么（职能域）**
```
你是数据查询执行者。接收SQL → 校验合理性 → 执行 → 返回结构化结果。
```

**2. 我不做什么（禁区——相邻Agent的地盘）**
```
你不做：数据分析（业务指挥官的事）、可视化（可视化Agent的事）、
搜索补充信息（信息采集Agent的事）、写入知识库（文档管理Agent的事）
```

**3. 我接收什么、输出什么（上下游接口）**
```
上游：中枢调度Z0、业务指挥官
下游：中枢调度Z0（由Z0转发）
输入格式：SQL语句 + 目标表 + 日期范围
输出格式：JSON结果集 + 行数 + 执行耗时（不包含分析文字）
```

**4. 遇到越界请求怎么办（拒绝协议）**
```
如果要求你分析数据：拒绝，回复"请将分析需求交给业务指挥官"
SQL有逻辑错误：指出问题，不自行修改，返回给上游确认
```

Agent 需要有"拒绝"的能力和指令。

### 防止目标漂移

集群里的目标漂移和传递失真比单 Agent 严重很多：
- 上游传递**只允许做减法**，不能做加法
- 每次执行层 Agent 用**新会话**，防止串上下文
- 设置**独立审计 Agent**

## 三、工程化 vs LLM 分工

### 不需要思考的步骤，就不该让 LLM 做

一个任务链路中，真正需要 LLM "动脑"的可能只有 30%：
- ✅ 判断舆情是正面还是负面 → 需要 LLM
- ✅ 决定数据异常意味着什么 → 需要 LLM
- ❌ 搬运、格式化、拼接、渲染、调用 API → 全部应该用脚本

### 脚本兜底 > Prompt 约束

LLM 记不住规则时静默违反；脚本校验不通过时明确报错阻止执行。

```python
# 工程化示例：SQL 前置校验
def sql_precheck(sql: str) -> dict:
    errors = []
    if "select *" in sql.lower():
        errors.append("禁止 SELECT *，请指定列名")
    if "limit" not in sql.lower():
        errors.append("必须包含 LIMIT 子句")
    return {"pass": len(errors) == 0, "errors": errors}
```

### 工程化五层

1. **知识持久化** — 跨 session 不丢
2. **流程模板化** — 高频任务固化成确定性链路
3. **前置校验** — 执行前先检查前提条件
4. **降级策略** — 定义失败时的退路
5. **版本管理** — Prompt 和规则当代码管，改坏了能回滚

## 四、Context 工程

### 核心原则

> Context Is All You Need

有效的 Context 能持续提供：
- 现在到底要解决什么问题
- 什么是不该做的
- 哪些约束不能破
- 当前已经做到哪一步
- 为什么之前做过某个决策
- 下一步应该沿着什么方向继续

### 渐进式披露

AGENTS.md 应该是 ~100 行的"地图"，指向更深层文档。巨型指令文件会挤占上下文、无法维护、无法机械验证。

### 开发前必须加载

- 过往开发的项目规范和项目记忆
- 验收标准和规范
- 代码标准（请研发来定）

### VibeCoding Tips

- 不要让 AI 自由发挥，基于标准框架来做，使用业内最佳实践
- 聚焦 MVP 功能打磨，一次只做一个功能模块
- Demo 阶段重逻辑轻页面
- **先 Plan 再 Coding**：让 AI 列计划，理清现状对齐目标
- 大型项目找 GPT 梳理需求，分模块给出技术方案，把技术方案丢给 CC/Codex 执行

## 五、评测体系

### 评测 Agent 准入门槛

AI 评测和人工评测的一致率 ≥ 0.85。Macro F1 ≥ 0.85（防止被多数类掩盖）。

### 稳定性观测

- 评级完全一致率 ≥ 0.85
- 多数一致率
- 逐检查项一致率 ≥ 0.85（定位不稳定维度）

即使 agent 打分和专家一致，输出不稳定仍然不能用于生产。

### 调优闭环

1. **对照分析**：输入 AI 评分 vs 人工评分对照表 → 输出结构化调优建议
2. **调优建议生成**：输入评分结果 + 人工反馈 → 输出调优文档
3. **应用调优**：输入调优文档 → 修改 skill 文件（逐条应用、三步回归验证）
4. **回归防护**：每次调优后必须重跑评测集，保证原本正确的不被破坏

### 五类规则

- **豁免规则**：提升 recall，减少误拦
- **约束规则**：同类 case 防止摇摆，提高稳定性
- **权威绑定规则**：规则和标准冲突时优先级
- **前置判断规则**：缩短推理链，减少出错
- **参考数据补充**：丰富 reference

### 人和 AI 的分工

| 人 | AI |
|----|-----|
| 定义对错 | 大规模执行 |
| 标注黄金测试集 | 批量评分和全量分析 |
| 审核调优方案 | 定位问题 |
| 判断边界 case | 回归验证、格式化输出 |

## 六、记忆系统设计

### 四类长期记忆

- **语义记忆**：用户画像（基本信息、偏好、性格）— 稳定的，与时空无关
- **情景记忆**：带时空标签的个人经历。在什么条件下用户会怎么反应
- **程序记忆**：用户的 SOP、行为习惯。以 skill 形式装载
- **事件记忆**：过去发生的具体事件

### 评估体系必须优先于功能开发

评估指标：存储准确率、提取准确率、场景匹配度

### 三条黄金标准

1. 记忆可被模型稳定准确调用（非碰运气召回）
2. 可更新（衰减、强化、修正，基于用户行为持续演进）
3. 可解释（为什么这么记、为什么这么用，拒绝黑盒）

### 关键设计抉择

- 用户画像不仅是标签集合，要包含近期状态、性格特征
- 情境记忆和事件记忆分开（前者预判，后者回溯）
- 预留衰减、强化、修正机制——**V1 不做衰减，6 个月后补的成本极高**

### 三个认知陷阱

- ❌ "记得多" = "懂得深"（没有结构化的记忆 = 噪声）
- ❌ 记忆是"上下文补充材料"（应该是"决策驱动器"）
- ❌ 用"场景驱动"掩盖"能力底座"缺失（统一记忆底座 + 场景验证）

## 七、Anthropic 官方 Harness 模式

源自 [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)：

### 三 Agent 架构（Planner → Generator → Evaluator）

- **Planner**：把简短 prompt 展开为功能列表
- **Generator**：每次只做一个功能，完成后 commit + 更新 progress
- **Evaluator**：独立 Agent，无可写权限，从新鲜上下文评估质量

### 结构化功能列表（JSON 不是 Markdown）

JSON 更不容易被 Agent 修改或删除。Agent 只允许改 `passes` 字段。

### 每条 session 的标准流程

1. 运行 `pwd` 确认位置
2. 读取 progress 文件和 `git log`
3. 读取功能列表，选一个未完成功能
4. 只做这一个功能
5. commit + 更新进度
6. 环境保持 merge-ready 状态

### 关键洞察

**同一个 session 做完所有事 ≠ 正确的目标。** 正确的目标是让不知道上个 session 发生了什么的 Agent 也能继续工作。

## 八、OpenAI Harness Engineering 六大概念

源自 OpenAI 的 [Harness Engineering](https://openai.com/index/harness-engineering/)：

1. **仓库即真相**：不在仓库里的东西，对智能体就不存在
2. **地图而非手册**：AGENTS.md ~100 行，指向更深文档
3. **机械化执行**：Lint 规则 > Markdown 文档。文档会腐烂，Lint 规则不会
4. **智能体可读性**：选"无聊"技术（API 稳定）、应用可 worktree 启动
5. **吞吐量改变合并理念**：纠错成本低，等待成本高。PR 生命周期短
6. **熵管理 = 垃圾回收**：智能体会复现坏模式，需要定期后台任务扫描
